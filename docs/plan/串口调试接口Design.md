# 串口调试接口 Design

## 1. 目标

为设备增加串口调试能力，使串口可以承载与 MQTT 一致的主要业务消息：

- 主机通过串口下发与 MQTT 下行相同的 JSON 命令。
- 设备通过串口输出与 MQTT 上行相同的 JSON 消息。
- MQTT 与串口可以同时工作，串口主要用于本地调试和问题定位。

串口不引入一套新的设备协议，设备属性、动作、事件以及 `msg_id` 等语义继续以现有 MQTT 协议为准。

## 2. 约束

设备只有一个可用串口，该串口当前还承担固件日志和烧录相关功能，因此不能按“日志串口 + 独立协议串口”的方式设计。

设计上需要在同一个串口中区分两类内容：

1. 普通运行日志。
2. 可被调试工具稳定识别的业务消息。

应用启动前的 ROM、bootloader 日志不受业务代码控制，调试工具也必须能够忽略这些内容。

## 3. 总体设计

串口调试默认关闭。收到明确的启动命令后，串口才作为一个与 MQTT 并行的调试通道工作。该状态不属于设备业务模式，也不改变现有 WiFi/BLE 模式。

```text
MQTT 下行 -----+
               +--> 统一消息入口 --> 属性设置 / 查询 / 动作 / OTA 命令
串口下行 -----+

设备上报/响应 --> 统一消息出口 --> MQTT
                              +--> 串口
```

核心原则：

- 下行只保留一套解析和业务处理逻辑。
- 上行只生成一次 JSON，再按各通道的可用状态并行分发给 MQTT 和串口。
- 串口调试不是 MQTT 的替代模式；两个通道同时可用时，同一条上行同时发送两份。
- 设备业务代码不感知消息最终通过哪个通道发送。
- 串口通信异常不能影响 MQTT 和设备控制任务。

## 4. 单串口复用

### 4.1 启动调试会话

设备复位后处于 `CLOSED` 状态：

- 串口保持现有日志输出。
- 不向串口镜像 MQTT 业务上行。
- 仅监听固定的调试启动命令，其他业务命令不执行。

启动命令定义为：

```text
@DEBUG START
```

设备收到完整启动命令后：

1. 先使串口消息出口可用，但暂不接收业务命令。
2. 如果设备尚未 first ready，则触发一次设备 first ready 初始化。
3. 初始化完成后切换到串口调试 `ACTIVE` 状态。
4. 通过统一串口输出出口返回一条带设备身份的完整就绪标记：

```text
@DEBUG READY {"device_id":"aabbccddeeff","firmware_version":"v1.1.38"}
```

`device_id` 是 `esp_efuse_mac_get_default()` 返回的 6 字节基础 MAC，编码为 12 位小写、无分隔符字符串，与 MQTT topic 使用的设备 ID 相同。`firmware_version` 原样读取 `esp_ota_get_app_description()->version`，包括 `PROJECT_VER` 中的前导 `v`。身份载荷由公共 `device_identity` 模块使用 cJSON 生成，串口与 BLE 不分别拼接 JSON。

主机只有收到字段完整且格式合法的新版 `@DEBUG READY` 后，才开始发送 `@CMD` 并解析 `@MSG`。仅返回 `@DEBUG READY` 的旧固件不允许以 COM 口生成临时身份，主机必须拒绝并释放该端口。启动命令是串口控制命令，不属于 MQTT 业务协议。

如果设备 first ready 初始化失败，设备保持串口调试 `CLOSED`，记录错误但不得重启，也不得返回 READY。主机按探测超时处理并释放端口，避免把业务硬件未就绪的设备误判为可控制设备。

first ready 初始化期间不向主机输出 `@MSG`；进入 `ACTIVE` 后主动发送一次当前属性快照，保证主机获得完整初始状态。

设备在 `ACTIVE` 状态再次收到 `@DEBUG START` 时，也必须重新返回完整的身份 READY，随后重新发送当前属性快照。这样主机可重复握手，不需要为了确认端口身份而复位设备。

设备复位后调试状态自动关闭。是否增加主动停止命令，可在实现阶段按调试工具需要决定。

### 4.2 行级复用

业务 JSON 使用简单的行前缀。前缀属于串口传输层，不属于业务 payload。

示意格式：

```text
@MSG {"method":"report","device_type":"CUNZHI01","battery":85}
```

主机下发命令时使用相同思路：

```text
@CMD {"method":"get","key":"battery","msg_id":101}
```

其中：

- `@CMD` 和 `@MSG` 仅用于在单串口中识别帧类型。
- 前缀后的 JSON 内容与 MQTT payload 保持一致。
- 每条消息占一行，使用换行符结束。
- 合法身份 `@DEBUG READY <identity-json>` 之前的普通日志、ROM 日志和 bootloader 日志没有业务前缀，调试工具直接忽略。

具体前缀名称可以在实现前调整，但必须保留明确的帧标识。直接依赖“以 `{` 开头就是业务消息”容易受到日志内容影响，不建议作为正式约定。

### 4.3 串口所有权

应用层只能有一个模块负责该串口的初始化和业务收发，不能重复安装 UART 驱动。

普通状态和调试状态下，日志都可以继续通过该串口输出。所有应用层日志和业务消息必须经过同一个输出仲裁，保证每次只向 UART 写入一条完整内容，业务消息不能被日志拆开。

DIANJI 中现有的 UART 初始化需要并入统一串口管理，不能继续单独初始化同一个 UART。

## 5. 消息流

### 5.1 串口下行

1. 串口模块按行接收数据。
2. `CLOSED` 状态只识别 `@DEBUG START`。
3. `ACTIVE` 状态识别 `@CMD`，取出后面的 JSON payload。
4. 将 payload 提交到统一消息入口。
5. 复用 MQTT 当前的 `set`、`get`、`update`、`action`、`ota_update` 等处理逻辑。

串口下行不伪造 MQTT topic。业务逻辑如果确实需要来源信息，应显式使用 `source=serial`，而不是传入一个假的 topic。

### 5.2 设备上行

设备产生 report、update、action、事件或命令响应时，先生成统一 JSON payload，再按当前连接状态分发：

- MQTT 已连接时发送到现有发布主题。
- 串口调试处于 `ACTIVE` 状态时输出为 `@MSG <payload>`。
- BLE 保持当前属性特征和消息特征的行为，并通过只读 `0xFF04 Identity` 特征返回与串口 READY 完全相同的身份 JSON；该特征在切换 BLE mode 前即可读取。

各发送条件独立判断，不使用互斥的 `if/else` 路由。因此 MQTT 和串口同时可用时，同一 payload 会同时发送到 MQTT 和串口。通过任一通道下发命令所产生的响应，也遵循相同的多路分发规则。

串口不回显收到的命令原文，只输出设备真正产生的上行消息。

## 6. 模块职责

### 6.1 统一消息入口

负责接收来自 MQTT、BLE 和串口的 payload，并顺序执行消息解析和设备操作。这样可以避免多个通信任务同时修改属性或控制硬件。

### 6.2 统一消息出口

负责将业务对象序列化为 JSON，并分发给 MQTT、串口和现有 BLE 通道。

当前散落的直接 MQTT 发布必须收敛到此出口，否则串口会漏掉部分 report、get 响应和 OTA 状态。统一出口在发送 MQTT 前检查真实的 connected 状态，未连接时跳过 MQTT，但不影响串口发送。

### 6.3 串口适配层

只负责：

- 从共享串口识别 `@CMD` 帧。
- 向共享串口输出完整的 `@MSG` 帧。
- 管理 `CLOSED`、启动切换和 `ACTIVE` 状态。
- 仲裁普通日志与业务帧的串口写入。
- 处理半行、连续多行、非法行和过长行。
- 隔离串口异常，不直接实现设备业务逻辑。

## 7. 日志共存策略

**仅使用按行和前缀，不能彻底解决 `ESP_LOG` 与业务消息互相干扰。** 如果日志任务和业务任务通过不同路径同时写同一个 UART，一条 JSON 仍可能被日志字节插入，前缀只能帮助识别，不能修复已经损坏的 JSON。

首版保留运行日志，但增加统一的应用层输出仲裁：

- `ESP_LOG` 输出和 `@MSG`/`@DEBUG` 业务帧共用同一个串口写入锁或发送队列。
- 每条业务帧以一次完整写入提交，持有输出所有权直到换行符发送完毕。
- 项目中的直接 `printf` 应改为 `ESP_LOG` 或统一输出接口，不能绕过仲裁模块。
- 调试工具只解析 `@MSG` 和 `@DEBUG` 开头的完整行，其他行仍作为普通日志显示或忽略。

这样可以避免正常应用运行期间的日志把业务 JSON 拆开，同时保留调试日志。bootloader 日志发生在应用启动和串口调试激活之前，不参与应用层仲裁，主机直接忽略其业务解析。panic 表示应用已经异常终止，输出崩溃原因、寄存器和调用栈后设备会重启；此时允许当前业务帧失效，主机应结束本次 ACTIVE 会话并等待设备重新启动。

ROM、bootloader、panic 以及少量绕过普通日志接口的底层输出无法由应用层写入锁约束，但它们不属于正常 ACTIVE 会话中的持续输出，不需要为此关闭正常运行日志。

## 8. 生命周期

本设计将 first ready 定义为“至少存在一个有效控制通道”，MQTT、BLE 和已启动的串口调试会话都可以满足该条件。

- 串口初始化不改变 `g_device_mode`。
- 设备启动和复位后串口调试默认为关闭。
- 串口收到 `@DEBUG START` 后，如果设备尚未 ready，则触发一次 `device_first_ready()`。
- first ready 必须使用线程安全的一次性状态，防止 MQTT 和串口同时就绪时重复创建任务。
- 串口先触发 first ready 后，MQTT 后续连接不重复初始化；MQTT 只加入上行分发，并继续完成订阅等 MQTT 自身流程。
- MQTT 已经触发 first ready 时，串口启动不重复初始化，只进入 `ACTIVE` 并发送当前属性快照。
- 进入 `ACTIVE` 后，即使 MQTT 未连接，串口命令、周期上报和命令响应也可以正常走串口。

串口触发 first ready 时，保留现有的 OTA 固件有效确认和连接指示行为；这里的“已连接”表示已有可用控制通道，不特指 MQTT 网络连接。

## 9. 错误与安全

- 非法前缀、非法 JSON 和不完整命令不得进入业务处理。
- `CLOSED` 状态下除 `@DEBUG START` 外的输入不得执行设备命令。
- 一条错误消息不能影响下一条合法消息的接收。
- 串口发送失败或拥塞不能阻塞关键设备控制任务。
- 串口拥有与 MQTT 下行相同的控制权限，包括设备动作和 OTA 命令，应视为高权限物理调试接口。
- 是否在量产固件启用串口命令，需要由产品和安全策略决定。

除 `@DEBUG READY <identity-json>` 这类会话控制应答外，首版不增加串口专用的业务命令 ACK 或错误 JSON。业务响应继续遵循现有 MQTT 协议，避免串口和 MQTT 形成两套语义。

## 10. 设计边界

本设计包含：

- 单串口上的日志与业务消息复用。
- 默认关闭并通过 `@DEBUG START` 显式启动调试会话。
- 每次 `@DEBUG START` 都返回 `device_id + firmware_version`，并在 READY 后发送属性快照。
- 串口启动可触发一次设备 first ready，支持无 MQTT/BLE 连接时完整启动设备任务。
- MQTT 与串口同时可用时并行发送同一业务 payload。
- MQTT/串口共用上下行业务协议。
- 消息入口和出口的统一方向。

本设计暂不确定：

- 缓冲区、队列深度和任务优先级。
- 具体 UART 驱动接管方式。
- 是否需要不复位即可退出调试会话。
- 量产固件是否默认开放串口命令。

这些内容在 Design 确认后进入实现方案和任务拆分。
